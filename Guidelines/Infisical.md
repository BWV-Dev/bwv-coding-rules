# Infisical Usage Guide

Infisical centrally manages project environment variables and secrets, allowing the team to use shared configuration without exchanging `.env` files.

URL: [https://vault.briswell-vn.com/](https://vault.briswell-vn.com/).

## Workflow Summary

1. [**Install the Infisical CLI** — Install the tool on your workstation](#1-install-the-infisical-cli).
2. [**Project Leader sets up the project** — Create a project, configure the repository and the application, and invite project members](#2-project-leader-sets-up-the-project).
3. [**Members use Secrets Management** — Manage secrets, use overrides, and run the application](#3-members-use-secrets-management).

## Step-by-Step Instructions

### 1. Install the Infisical CLI

👤 Responsible: Project Leader and Members.

Choose one installation method:

**Windows:**

```powershell
winget install infisical
```

**macOS:**

```bash
brew install infisical/get-cli/infisical
```

**Machines with Node.js/npm installed:**

```bash
npm install --global @infisical/cli
```

Open a new terminal and check the installation with `infisical --version`. The project configuration file `.infisical.yaml` needs version **0.43.145 or later**. To upgrade an existing installation, run `winget upgrade infisical`, `brew upgrade infisical`, or `npm install --global @infisical/cli@latest`. For Linux installation and other options, see the [CLI installation docs](https://infisical.com/docs/cli/install).

### 2. Project Leader sets up the project

👤 Responsible: Project Leader.

#### 2.1. Create a project in Infisical

- Log in to [vault.briswell-vn.com](https://vault.briswell-vn.com/) and select the BWV-Dev Organization (or the appropriate Organization for the project).
- In **Secrets Management**, select **Create Project** and name it after the project, for example `bwv-infisical-management`.
- Use the **Development** environment (slug `dev`) and create application folders if needed, for example `/backend`.
- In the project's **Settings**, delete the **Staging** and **Production** environments that Infisical creates by default. The team only uses Infisical on members' workstations, so only **Development** is needed.

#### 2.2. Configure the repository

From the repository root, log in and select the project you just created:

```bash
infisical login --domain=https://vault.briswell-vn.com
infisical init --domain=https://vault.briswell-vn.com
```

The CLI creates **`.infisical.yaml`** (with a leading `.`). Update the configuration as follows:

```yaml
general:
  domain: https://vault.briswell-vn.com
secrets-management:
  project-id: <PROJECT_ID>
  default-environment: dev
```

- Keep the `project-id` generated by the CLI.
- `domain` points the CLI to the company instance and `default-environment` selects the environment, so `infisical run` does not need `--domain` or `--env`. Keep `--domain` on `infisical login`, which may run outside the repository.
- The file only contains project configuration and can be committed. `domain` decides where the CLI sends your credentials, so review any change to it as carefully as a code change.
- A repository that still has the older `.infisical.json` keeps working. To convert it, run `infisical migrate-config` in the repository root; the command creates `.infisical.yaml` and deletes the JSON file.

**If the project uses several branches with their own environments**, map the branches to environments in the same file:

```yaml
secrets-management:
  project-id: <PROJECT_ID>
  default-environment: dev
  mappings:
    git-branch-to-environment:
      develop: dev
      phase1: phase1
```

- The CLI picks the environment from the branch checked out when a command runs, so switching branches switches the secrets without changing any command. Branches without a mapping use `default-environment`, and `--env` on a command overrides both.
- Only the part of the branch name after the last `/` is matched. `release/v1.2.0` matches the key `v1.2.0`, so branches with a prefix such as `feature/` or `release/` cannot be mapped as a group and use `default-environment`.
- Create each mapped environment in the Infisical project before committing the mapping, for example a `phase1` environment for the configuration of the `phase1` branch. After setup, the project only has **Development**.
- Do not store production secrets in these environments; they are loaded on members' workstations.

For details, see the [project configuration docs](https://infisical.com/docs/cli/project-config).

Then configure how the application loads the secrets ([2.3](#23-configure-the-application)), and commit `.infisical.yaml` together with those changes so all members use the same configuration.

#### 2.3. Configure the application

##### Node.js

Update `scripts` in `package.json` to run the application through Infisical:

```json
{
  "scripts": {
    "dev:infisical": "infisical run --path=/backend -- npm run dev:app",
    "dev": "node --watch src/server.js"
  }
}
```

- `node --watch src/server.js` is only an example. Keep the other scripts unchanged.
- Replace `/backend` with the folder containing the application's secrets; use `/` if they are stored at the root.

##### PHP with Docker

The application must read its configuration with `env()`. Laravel's `config/*.php` already does. CakePHP's `config/app_local.php` is not committed, so put the `env()` calls in `config/app_local.example.php` and ask members to recreate their `app_local.php` from it.

In `docker-compose.yml`, list the application's variables under `environment` of the service that runs PHP. Docker Compose copies their values from `infisical run` into the container:

```yaml
services:
  app:
    # ...existing configuration
    environment:
      - APP_KEY
      - DB_HOST
      - DB_DATABASE
      - DB_USERNAME
      - DB_PASSWORD
```

- List every variable the application reads from Infisical. A variable that is not listed does not reach the container, so add its name here when you add it in Infisical.
- Write the start command in the project's README so members use the same folder:

  ```bash
  infisical run --path=/backend -- docker compose up -d --build
  ```

  Replace `/backend` with the folder containing the application's secrets; use `/` if they are stored at the root.

##### PHP with Laragon

As with Docker, the application must read its configuration with `env()`. No other change is needed in the repository.

Write in the project's README the PHP version and, if the secrets are not stored at `/`, their folder. Members set them in the `projects.json` of laragon-dev ([3.3](#33-run-the-application)).

#### 2.4. Invite members to the correct project

- If a member has not joined the Organization, invite them using their company email with the **Member** role; ask an Organization Admin for help if you lack permission. Copy the invitation link and send it to the recipient.
- Open **the relevant project → Access Control → Users → Add Users to Secrets Management**, select the member, and assign a role:
  - **Viewer:** read secrets, suitable for members who only need to run the application.
  - **Member:** read and edit secrets.
- **Only add members to projects they work on.** Joining an Organization does not grant access to every project; do not assign Organization Admin to regular members.
- When a member leaves the project, remove their access to that project.

### 3. Members use Secrets Management

👤 Responsible: Members; editing requires the Member or Admin role in the project.

#### 3.1. Add and update secrets

- Open the correct project, select **Development** (or the environment mapped to your branch), and navigate to the application's folder.
- Select **Add Secret** and enter the variable name and value, for example `DATABASE_URL` or `JWT_SECRET`.
- Use the import feature to migrate multiple variables from `.env` if needed.
- For Laravel, generate `APP_KEY` with `php artisan key:generate --show` and add the output as a secret; without `--show`, the command writes the key to `.env`.
- Shared values are used by members with access. Coordinate with the Project Leader before changing a value that affects the entire team.

#### 3.2. Use Personal Override

- Open the secret's three-dot menu → **Add Override**.
- Enter a value for your own workstation, for example a `DATABASE_URL` pointing to a local database.
- The override only applies when secrets are fetched using its creator's account; other members still receive the shared value.
- Docker and Laragon reach services differently, for example `DB_HOST=host.docker.internal` in a container and `DB_HOST=127.0.0.1` with Laragon. If your setup differs from the shared value, use an override.
- Delete the override to return to the shared configuration. If your local configuration differs from the team's, check overrides first.

For details about secrets and overrides, see the [Secrets Management docs](https://infisical.com/docs/documentation/platform/secrets-mgmt/project#personal-overrides).

#### 3.3. Run the application

After accepting the invitation, clone or pull the repository configured by the Project Leader. Members use the committed `.infisical.yaml` and do not need to run `infisical init` again.

##### Node.js

```bash
infisical login --domain=https://vault.briswell-vn.com
npm install
npm run dev
```

Infisical fetches secrets and injects them into the application's environment variables.

##### PHP with Docker

From the repository root, log in and run the start command from the project's README, for example:

```bash
infisical login --domain=https://vault.briswell-vn.com
infisical run --path=/backend -- docker compose up -d --build
```

After changing secrets or overrides, run the `infisical run ... docker compose up` command again; Compose recreates the container with the new values. `docker compose restart` keeps the old values.

##### PHP with Laragon

Windows only. The launcher needs Laragon's Apache and its Thread Safe x64 PHP builds (Laragon's defaults); see the [laragon-dev requirements](../tools/laragon-dev/README.md#requirements).

1. Clone the project into Laragon's `www` folder, for example `D:\laragon\www\my-project`, and select **Start All** in Laragon once so it creates the `my-project.test` site.
2. Stop Apache in Laragon and uncheck **Apache** in **Preferences → Services & Ports** so **Start All** does not start it again. Keep using Laragon for MySQL and the other services.
3. Install the launcher in `<laragon>\usr\dev\`; it finds Laragon from this folder:

   ```powershell
   New-Item -ItemType Directory -Force D:\laragon\usr\dev
   Copy-Item <bwv-coding-rules>\tools\laragon-dev\* D:\laragon\usr\dev -Recurse -Force
   ```

   Replace `<bwv-coding-rules>` with your clone of this repository and `D:\laragon` with your Laragon folder. Run the same commands to update the launcher; your `projects.json` is kept. Add `D:\laragon\usr\dev` to `PATH` to type `dev` instead of `D:\laragon\usr\dev\dev.cmd`.
4. If the project uses a PHP version other than Laragon's default, or its secrets are not stored at `/`, copy `projects.example.json` to `projects.json` in `D:\laragon\usr\dev` and set them:

   ```json
   {
     "projects": {
       "my-project": { "php": "8.2", "path": "/backend" }
     }
   }
   ```

5. Log in and start the sites:

   ```powershell
   infisical login --domain=https://vault.briswell-vn.com
   dev up
   ```

   The first run may show a UAC prompt to update the `hosts` file. Check that the output lists `🔑 my-project.test (N secret(s))`, then open `http://my-project.test`.
6. Run CLI commands with the project's PHP version and secrets:

   ```powershell
   dev run my-project composer install
   dev run my-project php artisan migrate
   ```

- After changing secrets or overrides, run `dev restart`.
- If the site is served from the wrong folder, Laragon has not created its site yet, so `dev up` uses `public\` or the project folder: run `dev down`, start Apache in Laragon once, stop it, then run `dev up`.
- Multi-line values such as PEM keys are not supported; store them base64-encoded and decode them in the application.
- For configuration options and troubleshooting, see the [laragon-dev README](../tools/laragon-dev/README.md).

#### 3.4. Notes

- After changing secrets or overrides, restart the application to load the new values (Node.js: run `npm run dev` again; PHP: see [3.3](#33-run-the-application)).
- Only pass public configuration to the frontend, such as `VITE_*` variables; values bundled into browser code can be viewed by users.
- **PHP:** do not cache the configuration locally. `php artisan config:cache` and `php artisan optimize` write the secret values to `bootstrap/cache/config.php`; if you ran them, run `php artisan config:clear`.
- **PHP:** in `phpunit.xml`, use `<server>` instead of `<env>` for test values. When PHP runs from the command line, as tests do, values from Infisical are in `$_SERVER`, which `env()` in Laravel and CakePHP reads first. `<env>` entries, even with `force="true"`, do not override them, so tests could run against the development database:

  ```xml
  <server name="APP_ENV" value="testing"/>
  <server name="DB_DATABASE" value="my_project_testing"/>
  ```

- **PHP:** after importing `.env` into Infisical, delete your local `.env`. Values from Infisical take precedence, but variables missing from Infisical would still be read from `.env`.

For advanced usage, see the [Infisical docs](https://infisical.com/docs) and [CLI reference](https://infisical.com/docs/cli/reference).
